# 信令协议

> 实现：`src/NexusP2P.Signaling/`
> 相关：[`protocol.md`](protocol.md)（数据通道上的传输协议）、[`wire.md`](wire.md)（文件码与分享链接）
>
> 网页端与 exe 都要照本文连接信令服务器。

## 服务器的职责边界

**只做两件事**：给两端配对，把 SDP / ICE 候选从一端转发到另一端。

**不做的事**：不解析转发的内容、不存储任何文件字节、不落盘。
房间只存在于内存里，进程重启全丢也不影响正确性 ——
续传的锚点是内容（清单哈希）而不是房间号（AD-4）。

转发的 payload 在服务端代码里是一个不透明的 `JsonElement`。
让「服务器看不到内容」由类型保证，而不是靠我们记得不去读它。

## 端点

| 端点 | 用途 |
|---|---|
| `GET /signal/create?maxReceivers=N&password=…` （WebSocket 升级） | 建房，占住发送方位子。`maxReceivers` 可省略，默认 1（V1 行为），服务器夹到 `[1, MaxReceiversPerRoom]`。`password` 可省略，设置后房间启用口令（最多 64 字符，超长报错 —— 建房方是自己人，没有预言机顾虑） |
| `GET /signal/join/{code}?role=receiver\|sender&password=…` （WebSocket 升级） | 用文件码进房。房间设置了口令时必须带正确的 `password` |
| `GET /health` | 健康检查：活跃房间数、PublicOrigin、是否配了中继 |

`role` 默认 `receiver`。发送方**重连**时用 `role=sender` 回到原来的位子。

> 位子归属不做鉴权。知道文件码的人可以抢占发送方位子，但这毫无收益 ——
> 抢位者手里没有源文件，造不出能通过验证的清单。
>
> **但要注意（V3）**：知道文件码的人可以抢占**接收方**位子并拿到文件 ——
> 密钥现在由发送方在通道里推送，文件码因此成为唯一凭证。这是「只念一串
> 数字就能收」的直接代价，见 [`protocol.md`](protocol.md) 的「密钥要约」。
> 可选口令（见下）就是在这一层加的第二道门槛。

## 可选口令（V4）

发送方建房时带上 `password` 查询参数，房间即启用口令；不带则一切与从前
完全一致（wire 上逐字节相同，旧客户端无感）。

- **校验位置**：信令服务器。服务器存 PBKDF2-SHA256 校验值（每房独立盐，
  10 万次迭代），**不存明文**。任何角色进房（含发送方重连）都要凭口令 ——
  否则宽限期里空出来的发送方座位就成了口令的旁门
- **失败不可区分**：口令缺失/错误返回与「码不存在」**完全相同**的
  `Unavailable`。口令不能给九位码引入新的枚举预言机；区分信息只进服务端日志
- **回显**：`created` 应答带 `passwordProtected: true`。客户端据此识别
  「我带了口令、但旧服务器没认」的静默降级并警告用户
  （与 `maxReceivers` 回显同一模式）
- **威胁模型**：口令经信令连接（WSS）传递，服务器看得到它。这与项目
  既有边界一致 —— V3 起密钥本身就经由信令协商的连接送达，传输内容的
  机密性依赖 AES-256-GCM 而不是口令。口令只挡「拿到文件码但没拿到口令」
  的人，因此要与文件码**分开渠道**传递，也永远不进分享链接
- **C# 客户端**：尚未实现口令参数（不传即不设口令，与从前一致）。
  用口令保护的房间只能由网页端进房；C# 端会得到与其他入房失败相同的
  「房间不可用」错误

## 房间成员（V2，AD-12）

一个房间 = **1 个发送方 + 至多 N 个接收方**（N 在建房时声明，默认 1）。

每个接收方进房时由**服务器分配**一个 `peerId`（8 个十六进制字符，
会话内标识，不持久）。peerId 不由客户端自报 —— 自报的标识既可能撞车
也可能被仿冒。

两条边界规则：

- **接收方之间互不可见**：`peer-joined` / `peer-left` 只发给发送方；
  接收方的 `signal` 一律只路由到发送方，带 `to` 也被忽略。
  V2.0 没有任何接收方互联的需求，多暴露一个面只是白送攻击面
- **接收方断线重连拿新 peerId**（AD-16）：发送方看到一次 `peer-left` +
  一次 `peer-joined`，为它新建链路。续传锚点是接收端自己的
  `.part` + 位图，peer 身份无状态

## 消息

全部是 UTF-8 的 JSON 文本帧。单条上限 **256 KiB**（一条 SDP 通常几 KB）。

### 服务器 → 客户端

| `type` | 时机 | 字段 |
|---|---|---|
| `created` | 建房成功 | `code`（九位无分隔）、`shareUrlBase`、`iceServers`、`maxReceivers`（生效值）、`passwordProtected`（口令是否生效；旧服务器不回此字段） |
| `joined` | 进房成功 | `iceServers`、`peerPresent`；接收方：`peerId`（自己的）；发送方（重连）：`peers`（在房接收方的 peerId 列表） |
| `peer-joined` | 有接收方进来了（只发给发送方） | `peerId` |
| `peer-left` | 成员走了 | 发给发送方时带 `peerId`；发给接收方时无 `peerId`（走的必然是发送方） |
| `signal` | 转发对端的信令 | `payload`（原样）；发给发送方时带 `from`（来源接收方的 peerId） |
| `error` | 失败，随后关闭 | `message` |

`shareUrlBase` 来自配置（AD-8）。客户端拼出完整链接：
`{shareUrlBase}/{code}`（V3 起链接里不再有密钥片段）。

`peerPresent`：接收方的 `joined` 里表示发送方是否在房；
发送方的 `joined` 里等价于 `peers.Count > 0`。重连要靠它 ——
断线重连是回到**已经有人的**房间，`peer-joined` 只在「进来的那一刻」发一次，
晚回来的一方永远等不到它。

### 客户端 → 服务器

只认一种：

```json
{ "type": "signal", "payload": <任意 JSON>, "to": "peerId（仅发送方，可选）" }
```

- **发送方**：多接收方房间里必须带 `to`（目标接收方的 peerId）；
  不带 `to` 时仅当房里恰好一个接收方才可路由（V1 客户端兼容，AD-15）。
  `to` 指向不存在的 peerId 时**静默丢弃** —— 接收方刚断线时发送方手里
  有过期的 peerId，这是正常时序而不是协议违规
- **接收方**：`to` 被忽略，`signal` 只到发送方

其他类型与畸形 JSON **一律忽略**，不断开连接 ——
为一条无意义的消息掐掉一条正常的信令连接不值得。

## 入房失败：绝不区分原因

**「码不存在」「码格式不对」「位子已被占」「席位已满」「口令缺失或错误」必须给出完全相同的错误消息。**
任何差异都会让九位码有了枚举预言机 —— 攻击者靠错误信息就能筛出活跃房间。

实现上把这件事做成**类型上不可能出错**：`JoinOutcome` 只有
`Joined` 和 `Unavailable` 两个取值，想区分也无从下手。
区分信息只写进服务端日志。

连「码格式不对」也走同一条路径：若在解析阶段提前返回 400，
「格式对但不存在」与「格式不对」就又有了差异。

## 限速

同一 IP 每分钟 **20** 次入房尝试（可配），**滑动窗口**。

- 限速在 **WebSocket 升级之前**执行，所以能返回真正的 `429` 加 `Retry-After`。
  升级之后就只能在应用层告知，客户端与中间设备都不认
- 算的是**全部**尝试而不只是失败的：只算失败会留一个
  「先成功一次刷新配额」的漏子，而正常用户一分钟内不会入房二十次
- 用滑动窗口而不是固定窗口：固定窗口在边界处允许两倍突发
- 拿不到 IP 时归到一个共享桶，**不是放行** ——
  「拿不到 IP 就不限速」等于给攻击者一条绕过路径
- 建房**不受**此限：它是自己发起的，不构成枚举风险

## 房间生命周期（AD-16：以发送方为锚）

```
建房 ──► 发送方占位 ──► 接收方陆续进出 ──► 转发信令
                │                        │
                └──── 所有成员都离开 ─────┘
                          │
                     60 秒宽限期
                       │      │
              宽限期内重连    宽限期过
                  │              │
              回到原房间       回收
```

- 发送方在而接收方来来去去：房间永不过期（正常状态）
- 接收方在而发送方不在：房间保留，等发送方宽限期内以 `role=sender` 回位
- **所有成员都离开**才起算宽限期 —— 网络抖动时全体信令连接
  往往同时掉线，若房间立刻释放，自动重连必然扑空（AD-7）

宽限期不破坏无状态性 —— 房间仍然只在内存里，仍然不落盘。

两个实现细节：

- **过期判定不依赖回收任务**。回收是定时跑的（15 秒一轮），
  所以「已过期但还在字典里」这个窗口一定存在；入房判定必须自己算过期
- **腾位子时校验「仍然是自己占着」**。旧连接的清理逻辑可能在新连接
  已经占位之后才跑到，不校验就会把刚重连上来的人踢下去

## 配置（AD-8）

| 键 | 默认 | 说明 |
|---|---|---|
| `Signaling:PublicOrigin` | **必填** | 对外公开的基址。缺了它服务**拒绝启动** |
| `Signaling:RoomGracePeriodSeconds` | 60 | 房间宽限期。调到 0 会让自动重连失效 |
| `Signaling:JoinAttemptsPerMinute` | 20 | 入房限速 |
| `Signaling:MaxRooms` | 1000 | 房间总数上限，防止内存被吃光 |
| `Signaling:MaxReceiversPerRoom` | 不限制 | 单房接收方席位上限（V2）。建房请求的 `maxReceivers` 被夹到 [1, 此值]。默认不设天花板，席位数由发送方按自己的上行带宽决定；公开部署想限制时配成具体数值 |
| `Signaling:Turn:Urls` | `[]` | TURN 地址（Task 3.3） |
| `Signaling:Turn:Secret` | — | 配了 Urls 就必须配它，否则启动失败 |

`PublicOrigin` **必须显式配置，不能从请求的 Host 头推断**：服务器绑定的地址
不等于对外公开的 URL（反代、NAT、端口映射都会让两者不同），
而 Host 头是客户端可控的 —— 用它生成链接等于把一个可污染的值写进
用户要分享出去的东西里。

配置校验在**启动时**跑（`ValidateOnStart`）并一次报出全部问题。
带着错配置跑起来的后果是生成一堆对方打不开的链接，
而这种错误很难从现象倒推回配置。
