# 传输协议

> 实现：`src/NexusP2P.Transfer/Protocol/`、`SendSession.cs`、`ReceiveSession.cs`
> 相关：[`hashing.md`](hashing.md)（哈希构造）、[`wire.md`](wire.md)（清单/文件码/加密）
>
> 网页端要实现收发时必须照本文来。
>
> **V3.0.0：新增 `KeyOffer`，接收方只需文件码。** 密钥不再由用户转述，
> 而是由发送方在通道建立后作为首条消息推送。这改变了威胁模型 ——
> 见下方「密钥要约」一节。**V3 与 V1/V2 不互通**：旧接收方遇到 `KeyOffer`
> 会报未知消息类型，新接收方遇到旧发送方会明确提示对方升级。
>
> **V2.0.0：数据通道协议无改动。** 一对多（AD-10）只是让发送方同时维护
> N 条本协议的独立会话（每接收方一条），协议本身的帧、消息与轮次完全不变。

## 分层

```
IDataChannel        消息式、有序、可靠、带 BufferedAmount 背压（贴合 WebRTC DataChannel）
  └─ 帧             类型 + 总长 + 偏移 + 本片长度，用来把大的逻辑消息切开
      └─ 逻辑消息    Manifest / Bitfield / Piece / PushComplete / Complete / Error
          └─ 会话    发送端与接收端的状态机
```

## 帧

```
u8   类型
i32  逻辑消息总长（大端）
i32  本片在逻辑消息中的偏移
i32  本片载荷长度
     载荷
```

帧头 13 字节。逻辑消息上限 **8 MiB**，解析时在分配之前校验 ——
否则对端只要声称一个天文数字的总长就能让我们 OOM。

**为什么需要切帧**：默认分片 1 MiB，而 DataChannel 单条消息的跨浏览器安全上限
只有 256 KiB。大文件夹的清单也一样（20 GiB 约 640 KiB 的分片根）。

**关键不变式**：一条逻辑消息的各帧在链路上**连续**，不与其他逻辑消息交错。
由「通道有序」+「发送方不交错投递」共同保证。接收侧因此只需要**一个**重组槽位，
并且会强制校验这一点 —— 一旦对端打破它就立刻报错，而一张任意键的重组表
会把这类错误悄悄拼成形状正确的垃圾数据。

## 消息类型

| 值 | 类型 | 方向 | 载荷 |
|---|---|---|---|
| `0x01` | Manifest | 发 → 收 | 用 manifestKey 密封的清单（见 wire.md） |
| `0x02` | Bitfield | 收 → 发 | `i32 分片数` + 位图字节 |
| `0x03` | Piece | 发 → 收 | `i32 文件序号` + `i64 分片序号` + 分片密文 |
| `0x04` | Complete | 收 → 发 | 空 |
| `0x05` | Error | 双向 | `u16 错误码` + UTF-8 文本（上限 4096 字节） |
| `0x06` | PushComplete | 发 → 收 | 空 |
| `0x07` | KeyOffer | 发 → 收 | 32 字节密钥材料（裸字节，无头部） |

位图末字节里超出分片数的位必须为 0，否则同一个位图会有多种字节表示。

Piece 消息**必须带位置**：加密 nonce 由 `(文件序号, 分片序号)` 派生，
接收方少了位置就解不开 —— 这同时让「把密文挪到别的位置」自动失效。

未知的**错误码**归到 `Unknown` 但保留原文（对端可能是更新的版本）；
未知的**消息类型**则拒绝（协议违规）。

## 密钥要约（V3）

**`KeyOffer` 必须是通道上的第一条消息。** 它承载本次传输的 32 字节密钥材料，
接收方用它派生 `contentKey` 与 `manifestKey`（派生方式见 wire.md，一字未改）。

### 为什么要有它

九位文件码能口头念，43 个字符的密钥不能。用户只能把密钥连同链接一起发到
聊天工具里 —— 而既然已经在用聊天工具了，不如直接发文件。密钥留在人的手里
就等于这套「念一串数字就能传文件」的设计不成立。

### 安全边界的变化（必须讲清楚）

| | V1 / V2 | V3 |
|---|---|---|
| 密钥位置 | URL fragment，规范保证不发往服务器 | 数据通道内，DTLS 加密 |
| 被动记录流量的服务器 | 拿不到 | 拿不到 |
| **主动做中间人的服务器** | **拿不到**（无法伪造能通过验证的清单） | **能拿到** |

也就是从「服务器在密码学上无能为力」退化为「服务器不主动作恶即安全」。
自建自用的信令服务器场景下这通常可以接受，但**必须写在用户看得到的地方**，
不能让人以为安全性没变。

想要回原来的强度，路子是 PAKE（把文件码本身当密码跑 SPAKE2/CPace），
那需要两端各实现一份密码学敏感代码，不在 V3 范围内。

### 实现约束

- **载荷恰好 32 字节**，多一个字节都算协议违规。「宽容地只取前 32 字节」
  会让实现分歧静默地变成解密失败，而那种失败在现场看起来像「文件码不对」
- **不对它做二次加密或混淆**。密钥总得有个源头，在明文通道上套一层
  「看起来像加密」的东西，只会让人误以为它比实际更安全
- **顺序是硬性的**。密钥晚于清单到达的话，清单在到手的那一刻就解不开，
  而「先缓存住等密钥来」会给攻击者一个免费的内存占用面
- 收到 `Manifest` 而不是 `KeyOffer` 时，报「对方是旧版本」而不是
  「期望 KeyOffer 实际 Manifest」—— 后者只有开发者看得懂

## 全局分片下标

Bitfield 是对**整次传输**的一张位图，所以需要一个连续的全局下标空间：
按清单里文件的顺序把各文件的分片拼接起来。清单是排好序的，
所以两端算出的映射必然一致。

落盘时用的是「文件内下标」。换算只有一个入口（`PieceLocator`）——
换算逻辑散落到多处是这类代码最容易出错的地方，偏移算错就是静默的数据损坏。

## 会话流程（轮次制）

```
发送端                                    接收端
  │                                         │
  ├── KeyOffer ─────────────────────────►   │ 取出密钥材料，派生两把密钥
  ├── Manifest ─────────────────────────►   │
  │                                         │ 解密 → 校验路径安全 → 打开仓储
  │                                         │ （查本地 .part 得到已有进度）
  │   ◄──────────────────────── Bitfield ───┤
  │                                         │
  │ 若位图已满 → 等 Complete                 │ 若位图已满 → 跳到收尾
  │                                         │
  ├── Piece × N（只发对端缺的）─────────►    │ 逐片解密 → Merkle 校验 → 落盘
  ├── PushComplete ─────────────────────►   │ 本轮结束
  │                                         │
  │   ◄──────────────────────── Bitfield ───┤ 还缺就再要一轮（回到上面）
  │                                         │
  │                                         │ 收齐 → 整体根校验 → 落到最终路径
  │   ◄──────────────────────── Complete ───┤
```

### 为什么要有轮次与 PushComplete

**没有它会死锁。** 接收方拒收一个分片（校验不过）是静默的，发送方不知道要重发，
于是接收方等分片、发送方等完成通知 —— 两边各等各的，传输永久挂死且没有任何错误。

有了轮次边界，接收方在一轮结束后重发位图请求剩下的部分，
被拒收的分片下一轮自然会被重传。

### 收敛保证

- 每轮必须**有进展**：接收方发现「一整轮下来一个分片都没补上」就报
  `PieceVerificationFailed` 并关闭，不再空转
- 轮数上限 **8**，超出即失败
- 连续拒收上限 **16**：防止对端在一轮里一直灌垃圾
- **失败必须关闭通道**。任一方的会话异常退出时都要主动关掉传输层，
  否则对端会一直等下去 —— 症状是「传输卡死且两边都不报错」，最难排查

### 断点续传

续传完全由 Bitfield 表达，**没有额外机制**：
发送方只发对端位图里缺的部分。所以「关掉程序、重开、生成新文件码」
也能接上 —— 锚点是内容（清单哈希）而不是会话。

## 重连（AD-7）

自动重试 **3 次**，指数退避 1s / 2s / 4s，之后转「等待手动重连」。

每次重试都建一条**全新的连接**，不做 ICE restart 也不做 SDP 重协商 ——
续传的锚点是接收端的位图而不是连接身份，所以「维持连接」没有价值，
而重协商的复杂度是实打实的。

### 什么该重试，什么不该

这是最容易做错的地方。把「文件码不对」重试三次只是白等七秒再报同一个错，
还会让用户以为是网络问题。

| 可重试 | 不可重试 |
|---|---|
| 通道断开 | 文件码不对 / 清单解密失败 |
| 帧解析失败（对端可能只是抖了一下） | 清单含非法路径 |
| IO 异常 | 磁盘空间不足 / 目标目录不可写 |
| | 对端违反协议（含缺少 KeyOffer） |
| | 分片反复校验失败 |
| | 用户取消 |
| | **不认识的异常** —— 盲目重连只会把真正的原因埋在三次重试之后 |

> 重连时发送方**会重发 `KeyOffer`**：每次重连都是一条全新的连接，
> 接收方是全新的会话状态。密钥本身不变（同一次传输用同一份密钥材料），
> 所以续传的位图依然成立。

### 状态必须可见

自动重试要暴露 `正在重连 2/3` 这样的状态给 UI。否则 3 次重试会把
「网络确实不通」静默推迟七秒，用户只看到一个卡住的进度条。

### 转手动之后

已收下的进度**必须保留**（`.part` + `.meta` 都在），
用户点「重连」时从断点继续，而不是从头开始。

## 背压

- 有 `bufferedamountlow` 事件就用事件，**不要轮询**。
  SIPSorcery 没有这个事件只能轮询，而 `Task.Delay(1)` 在 Windows 上实际睡 15.6ms，
  光轮询本身就能吃掉大半吞吐
- 缓冲超过高水位（默认 4 MiB）就暂停投递，回落到一半再继续
- 注意 `Send` 是**同步入队**：几百 KB 可以一瞬间全塞进缓冲区。
  「已发送分片数」是入队计数，不代表对端收到了多少 ——
  想知道真实进度只能看接收端的位图
