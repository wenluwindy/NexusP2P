# 线上格式：清单、文件码、加密

> 实现：`src/NexusP2P.Core/{Manifest,Codes,Crypto}/`
> 哈希构造另见 [`hashing.md`](hashing.md)
>
> **网页端必须逐字节复现本规范。** 清单哈希、nonce 派生、密钥派生
> 只要有一处不一致，两端就无法互通，而失败方式往往是静默的。

## 1. 传输清单

### 二进制布局（全部大端）

```
"NXP2PMAN"                8 字节 ASCII 魔数
版本                      u8  = 1
leafSize                  u32
pieceSize                 u32
条目数 N                   u32
  ── 每个条目（按路径序数升序）──
  路径 UTF-8 字节数        u16
  路径 UTF-8 字节
  长度                     i64
  文件根                   32 字节
  分片根 × ceil            32 字节 each   ← 个数由长度推导，不在流里
空目录数 M                 u32
  ── 每个空目录（按路径序数升序）──
  路径 UTF-8 字节数        u16
  路径 UTF-8 字节
```

**分片根的个数不写进流里**，由 `max(1, ceil(长度 / pieceSize))` 推导。
这样攻击者无法在这个字段上撒谎，也就无法诱导一次巨额分配。

### 规范化规则（决定清单哈希的稳定性）

- 条目与空目录都按 **`string.CompareOrdinal`**（UTF-16 码元序数）升序排列。
  选它是因为 JavaScript 的字符串 `<` 运算也比较 UTF-16 码元 —— 两端排序规则必须一致
- 解析时**强制校验已排序**。收到未排序的清单直接拒绝，
  否则同一份内容会有两个不同的清单哈希，续传的锚点就不唯一了
- 路径去重**忽略大小写**：Windows 上 `a.txt` 与 `A.TXT` 是同一个文件
- 同一个路径不能既是文件又是空目录

### 清单哈希

```
ManifestHash = SHA256( 0x10 ‖ 上述规范字节 )
```

前缀 `0x10` 与 `hashing.md` 里的 `0x00`~`0x03` 同属一个域分隔命名空间。

**这是一次传输的身份**，用来给接收端的 `.part` 文件命名。发送方每次重发生成
新的文件码，但同一份内容的清单哈希不变 —— 这正是「关掉程序、重开、
用新码续传」能成立的原因。

### 上限

| 项 | 上限 | 理由 |
|---|---|---|
| 条目数 | 100,000 | 防恶意清单诱导巨额分配 |
| 总分片数 | 4,000,000 | 约 4 TiB（1 MiB 分片），足够而有界 |
| 单条路径 | 1024 字节 | |
| 单个路径段 | 255 字符 | |

### 顶层文件夹名包含在路径里

发送文件夹 `MyStuff` 产出的路径是 `MyStuff/a.txt`、`MyStuff/sub/b.txt`。
所以接收端能自然重建目录结构，而不会把一堆文件散落进下载目录。
单文件传输的路径就是 `a.txt`。

## 2. 路径安全（接收端必须执行）

清单路径是**不可信输入**。以下一律拒绝，任一条不合法就整体拒绝清单：

| 类别 | 例子 |
|---|---|
| 目录穿越 | `../x`、`a/../../b`、`..` |
| 当前目录段 | `.`、`./a`、`a/./b` |
| 绝对路径 | `/etc/passwd` |
| **反斜杠** | `a\..\..\b` —— Windows 会当分隔符，只按 `/` 切分的校验看不见 |
| 冒号 | `C:/x`、`file.txt:hidden`（NTFS 备用数据流） |
| 空段 | `a//b`、`a/`、`/` |
| Windows 保留设备名 | `NUL`、`CON`、`PRN.txt`、`COM1`、`LPT9.dat` |
| 结尾点或空格 | `a.`、`a ` —— Windows 会静默去掉，校验目标与落地目标就不是同一个 |
| 控制字符 | `\0`、`\n`、`\t`、U+007F |
| Windows 非法字符 | `< > " \| ? *` |
| 双向文本控制字符 | U+202E 等，能让 `photo_txt.exe` 显示成 `photo_exe.txt` |

**纵深防御**：拼接成绝对路径后，再确认结果仍位于根目录之内
（比较时给根目录补上分隔符，避免 `C:\root-evil` 被当成在 `C:\root` 内）。

## 3. 文件码与分享链接

### 文件码

九位十进制，展示为 `111-111-111`。分三组只为**能口头念给别人** ——
这是它不用 base32 之类更紧凑编码的唯一理由。

- 生成用 CSPRNG，取值均匀分布于 `[0, 10^9)`
- **必须保留前导零**：`000-000-001` 是合法码
- 解析宽容：忽略 `- _ . 空格 制表符`、全角连字符 `－`、全角空格 `　`、
  各种破折号 `‐ – —`；全角数字 `０-９` 折算成半角

### 分享链接

```
{PublicOrigin}/r/111111111#{base64url(32 字节密钥材料)}
```

- 路径里用**无分隔的九位数字**（展示时才加连字符）
- 密钥是 base64url 无填充，恒为 43 个字符
- **密钥必须在 `#` 之后。** URL fragment 按规范永不随请求发往服务器 ——
  这是「服务器即使中继流量也无法解密」的全部依据。挪进路径或查询串
  就等于端到端加密失效
- `PublicOrigin` 来自配置。**服务器绑定的地址不等于对外公开的 URL**
  （反代、NAT、端口映射都会让两者不同），所以不能从请求的 Host 头推断
- 解析**与基址无关**：接收方拿到的链接可能来自任何域名或端口

## 4. 加密

### 密钥派生

```
contentKey  = HKDF-SHA256(ikm=密钥材料, salt=空, info="NexusP2P/v1/content",  L=32)
manifestKey = HKDF-SHA256(ikm=密钥材料, salt=空, info="NexusP2P/v1/manifest", L=32)
```

分用途派生**不是形式主义**：若清单与分片共用一把钥匙，两边的 nonce 空间
就会重叠，而 AES-GCM 下 nonce 重用会直接泄露明文异或值。用标签分开，
从结构上让这种重叠不可能发生。

标签带版本号 `v1`，这样日后改派生方案时不会与旧实现悄悄互通 ——
宁可明确地连不上，也不要用错的密钥解出垃圾。

### 分片加密

```
算法   AES-256-GCM，16 字节认证标签
nonce  文件序号(be32) ‖ 分片序号(be64)      // 恰好 12 字节
AAD    清单哈希（32 字节）
密文   加密数据 ‖ 认证标签
```

**nonce 唯一性是这里唯一可能造成灾难性后果的地方。**
nonce 不是随机的，而是由位置确定性派生 —— 一次传输里
`(文件序号, 分片序号)` 这对值唯一，所以 nonce 必然唯一。

⚠️ **必须把文件序号也放进 nonce。** 只用分片序号的话，同一次传输里
两个不同文件的第 0 片会撞 nonce。这是这套方案里最容易犯的错。

跨传输不会重用：每次发送生成新的密钥材料，所以密钥不同。
AAD 再绑上清单哈希，即使密钥泄露也无法把一次传输的密文重放进另一次。

认证失败时**必须清零目标缓冲区**，不把任何部分明文交给调用方 ——
平台对失败时缓冲区内容不做承诺，所以这条保证要自己做。

### 加密是传输层的，落盘存明文

接收端的 `.part` 文件里是**解密后的明文**。理由：

- Merkle 根是对明文算的，校验必须在明文上做
- 文件最终形态本来就是明文，存密文没有任何实际收益
- 存明文意味着续传**不需要持久化密钥** —— 新会话用新密钥，
  解密后与同一个 Merkle 根比对即可

## 5. 已知实现陷阱

写 TS 实现时特别注意这几处 —— 它们都是 .NET 侧实际踩过的：

1. **`Base64Url.TryDecodeFromChars` 在 .NET 里会抛异常**（名字里带 Try 却会抛）。
   分享链接是不可信输入，必须挡住，否则畸形链接会让程序崩掉而不是提示「链接无效」
2. **`ImmutableArray<T>` 的相等性是底层数组的引用相等**，不是逐元素比较。
   record 自动生成的 `Equals` 会用上它，导致内容相同却判为不等
3. **`(byte)` 收窄在 checked 上下文里会抛 `OverflowException`**。
   有意截断要写成 `& 0xFF`
4. **前导零**：文件码用 int 存储时，格式化必须补齐 9 位
