# P2P 高速文件传输平台 — 方向文档

> 状态：方向已确认（2026-08-07）。**Phase 1、2 已完成并通过验收**，
> 传输库已选定。进度见 [`tasks/todo.md`](../../tasks/todo.md)。
>
> 传输库经过一轮 bake-off：SIPSorcery 只有 0.3 MiB/s（其 SCTP 拥塞窗口不增长，
> 参数是编译期 const 绕不过去），**改用 libdatachannel 后达到 75.8 MiB/s**。
> 架构没变 —— 换的只是实现，因为 WebRTC 的价值在 ICE 而不在 SCTP。
> 决议见 [`docs/adr/001-webrtc-implementation.md`](../adr/001-webrtc-implementation.md)。

## Problem Statement

我和朋友要临时传 10~20GB 的文件，怎么做到「发一串能口头念的码 → 对方点开就收 →
跑满物理带宽 → 传完关掉什么都不剩」，而我不为存储付费、不被限速、不被压缩？

## 用户与场景

只有我和几个朋友用，不推广、不注册、无账号。两个场景：

- **跨公网 1对1，10~20GB**（主场景，约 90%）→ 需要 NAT 打洞 + 中继，不需要 swarm
- **学校局域网 1对多**（次场景）→ 需要 swarm，不需要打洞

这两个场景在技术上互斥，是两条独立的代码路径，可以分两期做，互不阻塞。

### 一个决定项目节奏的数字

20GB / 50Mbps 家庭上行 ≈ **53 分钟**。

所以断点续传和后台运行不是加分项，是及格线——一小时的传输中断概率太高。
这也反过来说明网页端不该承担 20GB 的任务（没人会开着标签页等一小时）：
网页的真实定位是**小文件 + 即时收发**，大文件天然属于 exe。

## Recommended Direction

### 灵魂：文件码即产品

界面就是一串码，形如 `111-111-111`（9 位十进制，10 亿组合，分三组便于口头念）。

码里只承载房间号；**加密密钥放在 URL fragment（`#` 之后）**，浏览器规范保证
fragment 永不发往服务器，所以服务器从密码学上就无法解密任何字节，即使它正在中继这些流量。

码不过期——房间随发送方退出而蒸发，所以「不过期」的实际含义是
「会话存活期内一直有效」。每次重新发送生成**新码**，不复用旧房间号；
续传的锚点是 Merkle 根而不是房间号（见下）。

无账号、无文件列表、无历史。

### 骨架：按场景切分的双路径

| 场景 | 发现 | 传输通道 | 兜底 |
|---|---|---|---|
| 跨公网 1对1 | 信令服务器 + STUN | WebRTC DataChannel | coturn 中继（不限速） |
| 同局域网 1对多 | 信令服务器（ICE host candidate 自动选中内网路径） | WebRTC DataChannel，可选 QUIC 升级 | 同上 |

**局域网不做 mDNS 发现**：ICE 交换候选地址时天然包含 host candidate（本机内网 IP），
同一局域网的两个 peer 会自动选中这条最短路径。局域网直连是 WebRTC 免费送的，
只要双方都能连到信令服务器。这块工作被彻底删除。

QUIC 升级（若做）的触发条件是「**双方在同一局域网**」，不是「双方都是 exe」——
因为跨公网时瓶颈是家庭上行带宽，换协议一秒都省不了；只有局域网千兆环境下
协议开销才真正成为瓶颈。这属于二期的可选优化。

### 共享地基：分片层

BitTorrent v2 (BEP-52) 式的 Merkle 树，**SHA-256**，
**64 KiB 叶子块 / 1 MiB 分片**，任意分片可独立校验。

> 实现时定的两处：哈希用 SHA-256 而非 BLAKE3（浏览器 Web Crypto 原生支持，
> BLAKE3 要塞 WASM）；叶子放大到 64 KiB（不与 BitTorrent 互操作，
> 所以可以把哈希次数降到 1/4）。详见 `docs/formats/hashing.md`。

这一层定好，断点续传、跨会话恢复、swarm、多源下载全部是**推论而非新功能**。

### 续传机制

接收方把未完成内容写为 `.nexusp2p/<清单哈希>.<文件序号>.part`
加一份 `.nexusp2p/<清单哈希>.meta`（已完成分片位图）。

发送方重发同一文件时会生成新码，但内容不变所以**清单哈希不变**；
接收方据此找到同一批 part 文件 → 校验 → 从断点继续。
`.meta` 只是加速手段，丢失或损坏则全量重扫（SHA-256 跑 20GB 约 10~20 秒），
删了也不会坏。

> 实现说明：最初按「文件根」给 `.part` 命名（内容寻址，跨传输还能复用），
> 但一次传输里内容相同的多个文件会撞名 —— 数据全写进同一个 `.part`，
> 收尾时第一个文件把它移走、后面的就找不到了。多个空文件必然触发。
> 改用「清单哈希 + 文件序号」后仍然满足续传需求，只失去跨传输复用这个锦上添花。

服务器全程不存任何文件字节，且**完全无状态**——房间只是内存里一个短暂的转发通道，
进程重启全丢也无所谓。

### 网页与 exe 的边界

跨会话续传需要持久化 `.part`。exe 天生能做；网页做不到（OPFS 有配额、
清缓存就没、换浏览器更没）。这条自然划出边界：

> Task 0.2 实测把「配额」这件事量化了：**普通窗口下四个浏览器的 OPFS 都能写到 5 GiB，
> 无痕/临时上下文里 Chromium 系不到 2 GiB 就 `QuotaExceededError`** ——
> 而 `navigator.storage.estimate()` 在那种情况下仍然报 6 GiB。
> 数据见 [`docs/spikes/browser-storage.md`](../spikes/browser-storage.md)。

| | 网页 | exe |
|---|---|---|
| 会话内断点续传 | ✅ | ✅ |
| **跨会话续传（关了程序还能接着传）** | ❌ | ✅ |
| 20GB 级文件 | 勉强 | ✅ |
| 文件夹 | ❌ | ✅ |
| 后台 / 托盘 | ❌ | ✅ |

一句话讲清楚：**「网页临时收发，exe 才扛得住大文件和文件夹。」**

exe 的定位是**可靠 / 无限制 / 后台**，速度快是副产品而非卖点。

### 进度呈现

文件夹传输显示**整体一个进度条**（不逐文件），带实时速度，
并**说明当前瓶颈**——这是个刻意的产品决定：用户看到 3MB/s 时第一反应是「是不是坏了」，
应该直接告诉他为什么。需要区分并展示的状态至少包括：

- `走中继中` —— 打洞失败，速度受服务器上行限制
- `对方下行已满` / `本机上行已满` —— 物理带宽到顶，这就是最快了
- `磁盘 IO 瓶颈` —— 网络还有余量，落盘跟不上
- `对方暂停 / 缓冲区背压` —— 接收端处理不过来

### 客户端形态

exe = .NET 后台服务 + 系统托盘 + WebView2 承载 UI。

**前端界面只写一遍，网页和 exe 共用**；exe 内部传输引擎是 .NET 原生的，
不受浏览器沙箱限制。对「用 Claude Code 开发」这个约束，这是最省工时的切法。

## 部署形态（家用服务器 + 公网 IP + 80 被封、**443 可用**）

> 2026-08-07 更新：实测确认 **443 未被封**（现有网站正常运行），
> 所以不需要非标端口，分享链接是干净的 `https://域名/r/111111111#密钥`。

- **证书**：Let's Encrypt **DNS-01** 验证签发。80 被封所以 HTTP-01 不可用；
  TLS-ALPN-01 虽然可行（它用 443），但要在验证期间抢占 443、与常驻服务冲突，
  DNS-01 不碰端口也不中断服务，更省事
- **网站**：ASP.NET Core 监听 **443**
- **中继**：coturn，3478 (UDP/TCP) + 5349 (TLS) + 一段 UDP 高端口
- 动态 IP 则配 DDNS
- **HTTPS 是硬需求，不是可选项**：WebRTC 的 `RTCPeerConnection` 和
  File System Access API 都只在 secure context 下工作。
  （exe 内嵌 WebView2 指向 localhost 也算 secure context，不受影响）

### 中继成本：在主场景里几乎为零

服务器在家里，主场景是「**我**发给朋友」。数据路径是
`我的机器 → 局域网 → 服务器 → 家庭上行 → 朋友`，而直连是
`我的机器 → 家庭上行 → 朋友`。**瓶颈都是同一条家庭上行，中继不额外变慢。**

代价只出现在「朋友 A 发给朋友 B」——那时数据占我家下行进、上行出，
我家成了双向瓶颈。按实际用法这是少数情况，所以「中继不限速」是合理决定。

## 开源积木（不自研任何协议）

- **WebRTC**：**libdatachannel**（经 `DataChannelDotnet` NuGet，自带预编译原生库）。
  实测 75.8 MiB/s，是 SIPSorcery 的 253 倍。决议见
  [`docs/adr/001-webrtc-implementation.md`](../adr/001-webrtc-implementation.md)
- **中继**：coturn —— 绝不自研中继
- **QUIC**（二期可选）：System.Net.Quic（.NET 内置，基于 MsQuic）
- **信令**：ASP.NET Core 9 + SignalR 或裸 WebSocket
- **分片/校验**：BEP-52 式 Merkle 树 + **SHA-256**（两端都原生支持）
- **加密**：AES-GCM，密钥由文件码的 URL fragment 携带
- **桌面**：WebView2 + 系统托盘，UI 复用网页
- **证书**：win-acme / acme.sh（DNS-01）

      —— ADR-001 只在回环上验证了吞吐。coturn 的凭据签发与配置已完成，

- [ ] **长时间传输的稳定性** —— 只测了 13.5 秒；20 GiB 跨公网要跑 50 分钟以上，

- [x] **各浏览器落盘策略的实际上限** —— 已实测（Task 0.2）

- [ ] **System.Net.Quic 在目标 Windows 版本上可用**
      —— 对 Schannel / Windows 版本有要求（仅影响二期的可选优化）

## MVP Scope

**In：**

- 跨公网 1对1：exe ↔ 网页、exe ↔ exe
- 选**单文件或文件夹** → 生成 `111-111-111` → 对方输码 → 直连 → 传输
- Merkle 分片 + 会话内续传 + **exe 端跨会话续传**
- 打洞失败自动落 coturn 中继
- 端到端加密（密钥在 URL fragment，不上服务器）
- exe 托盘常驻，关窗口不中断传输
- 整体进度条 + 速度 + **瓶颈说明**

**Out（明确推迟）：**

- swarm / 一对多 —— 二期
- QUIC 升级 —— 二期可选
- mDNS 局域网发现 —— **永不做**，ICE 已免费提供
- 网页端跨会话续传 —— 浏览器做不可靠，不做

**验收标准**：把一个 15GB 文件夹从我的机器传到朋友的 exe，
中途拔网线并关掉发送端程序，重开后（新文件码）从断点继续，最终 Merkle 根校验一致。

## Not Doing（和原因）

- **自研 NAT 打洞 / 自研传输协议** —— 能吃掉 80% 时间的泥潭，
  成品必然不如 libdatachannel + coturn
- **swarm 调度器（一期）** —— 主场景是一对一，收益为零。但分片格式和
  bitfield 交换的数据结构现在就设计对，二期换调度器是局部手术
- **mDNS / 局域网自发现** —— ICE 的 host candidate 已经免费解决
- **账号 / 登录 / 文件历史** —— 违背「关掉即焚」，且只有自己人用
- **服务端存储文件字节** —— 中继是过路不是落地。一旦落地，
  成本模型、法律责任、产品定位全变
- **码的过期与权限控制** —— 明确不要。风险是 9 位码可被枚举，
  用一条服务端速率限制（如同 IP 每分钟 20 次尝试）兜底即可
- **跨平台客户端（Linux/Mac）** —— 都用 Windows，
  WebView2 + 托盘比 Avalonia 省事得多
- **推广 / 注册 / 增长** —— 明确不推广，这解放了大量设计约束

## 备胎方案：已不需要

原备胎是「网页只 P2P 发送不 P2P 收」，用来应对「所有 WebRTC 候选库都达不到
吞吐门槛」的情况。**第一个候选（libdatachannel）就以 6 倍门槛通过，
备胎不必启用。**

保留这段记录只为说明：当时的判断是「换实现比退到自研 QUIC 更可能是正解」，
而结果确实如此 —— 退到纯 QUIC 会丢掉 ICE，而打洞是明确不自研的部分。
